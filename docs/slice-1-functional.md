## Composition and configuration

`AppServices.production` validates the app's processed Info dictionary. Supply `KEEPSAKE_SUPABASE_URL` (HTTPS project origin), `KEEPSAKE_SUPABASE_PUBLISHABLE_KEY` (`sb_publishable_…` only), and `KEEPSAKE_ENVIRONMENT` through an explicitly approved local build configuration. The existing bundle-identity gate still applies. `Configuration/Backend.xcconfig.example` is a template, not an active configuration; its local `Backend.xcconfig` counterpart is ignored. Xcode can consume a reviewed local file through `-xcconfig`; no file with live settings belongs in Git. Nothing defaults to the inactive hosted project.

Both checked-in project representations pin `supabase-swift` to exactly 2.55.6. Package resolution and the transitive lockfile are deferred to authorized dependency/native verification; no resolved graph is claimed. Public pinned source signatures were inspected rather than substituted with current-main APIs.

The backend owns one standalone SDK `AuthClient` and one operation queue. It intentionally does not construct `SupabaseClient`: that convenience client's pinned initializer starts its own auth subscriber, which can refresh before an app-owned sign-out latch is checked. SDK automatic refresh is disabled. Restoration, explicit Retry, foreground revalidation, OTP, event-listener registration, sign-out, and account-authorized database work use the queue. The registration's initial refresh is awaited in that queue. Each database operation uses a `PostgrestClient` bound to the validated session's token, with no shared mutable “current account” header and no automatic request retry. Expired tokens must refresh before a read or write. An offline restoration may identify the locally stored account for read-only cache use; it does not authorize mutation.

The app session owns one auth-event consumer. Events carry no tokens or trusted identity payload to UI; they request serialized revalidation. Same-account refresh preserves generation/navigation. A new account lifetime or sign-out fences old group revisions, cancels feature admission, and clears visible content. A completed cancelled operation may release its own task handle but may not publish UI/cache data or clear a newer handle.

## Local privacy and uncertain outcomes

Keychain service names include bundle, environment, and backend host, with no shared access group. The session key is explicit. SDK logging is nil. App code never puts tokens into preferences, cache JSON, views, or logs; OTP input stays transient. A protected nonsecret disk latch plus a namespaced Keychain latch survives sign-out interruptions, including a Keychain failure. Discovered account ownership is durably added before credential deletion. Cleanup verifies removal of only the app-owned SDK keys, invalidates that account's group state, then removes the latches. Real removal errors block re-entry; remote revocation failure after successful local cleanup is reported as a warning, not a restored login.

`AccountGroupCache` stores a single versioned record per authenticated UUID under Application Support/KeepsakeIdentity/<namespace>/<account>/group.json. It contains a confirmed solo group, last-check time, and pending creation UUID/canonical name, never routes or tokens. Reads validate owner/schema/name and bounds; corruption fails closed. Writes atomically replace protected, backup-excluded files and synchronize the file before returning. This is source intent, not a hardware or power-loss durability proof.

Creation is offered only after an authoritative no-group read. The journal must be saved before dispatch. An uncertain result or relaunch retains the exact UUID/name; reconciliation reads first, then replays that operation only if absent. A competing-operation response reloads and explains the already-existing group without claiming the proposed name was saved. A definitive name validation rejection releases the journal only after its durable clear. A successful online result whose snapshot save fails remains confirmed online with an explicit offline-cache warning.

## Migration boundary

`supabase/migrations/20261118125134_slice1_private_solo_group.sql` is authored source, not an applied migration. The migration intentionally uses non-replacing creation statements: a collision with `private`, `groups`, `group_members`, the writer role, or either RPC/helper name must stop for reconciliation, not overwrite existing objects. Available repository source had no existing Supabase schema; that says nothing about hosted state. The target's exposed schemas, existing grants/default privileges, function-owner transfer capability, PostgreSQL UTF-8 support, and named-role feasibility must be inspected in an authorized safe environment first. `private` must remain outside exposed API schemas.

Paired foreign keys and uniqueness constrain one private group to exactly its owner membership. A narrow invoker RPC calls an unexposed definer helper owned by a NOLOGIN, non-BYPASSRLS, non-table-owner role. Only owner-scoped SELECT/INSERT is granted to that role; clients receive SELECT plus the exact function execution grants, not direct table writes or role membership. Owner identity comes from `auth.uid()`, never parameters or editable metadata. Name canonicalization trims outer U+0020, uses NFC and scalar count, and explicitly checks Unicode whitespace/control ranges rather than depending on database locale classification. Unicode fixtures still require actual target execution.

The helper uses insert-on-owner-conflict/do-nothing plus a subsequent READ COMMITTED read. Same operation/name returns the original row; conflicting names cannot rename; a different operation reloads the winner. Any membership/constraint failure aborts the transaction. There is no rename/delete/invite/member editor, sharing, profile, location, or recorder schema.

## Evidence required before acceptance

The new `SliceOneLifecycleTests` and `SliceOneStorageTests`, existing auth/session/shell tests, pgTAP security/rollback fixtures, and two-session concurrency spec are authored but uncompiled and unrun. Property-list lint, project/source membership checks, diff hygiene, and source review are not substitutes for them. The PostgreSQL isolation spec expects one `created` and one `replayed` for identical requests; distinct requests expect `KSG02` for the loser. Both schedules must finish with exactly one group and one owner membership. Its runner and checked expected output remain a verification task.

Keep the follow-up draft until a separately authorized exact-head native pass and isolated backend/test-inbox pass establish real delivery, restoration, refresh, device-local sign-out, account isolation, atomicity, denied cross-account/direct access, and lost-response/concurrent retry behavior. No production wake, deployment, migration, external mail, physical-device access, merge, or release is implied.
